# Отчёт по результатам анализа Kubernetes Audit Log

## Подозрительные события

1. Доступ к секретам:
   - Кто: system:serviceaccount:secure-ops:monitoring
   - Где: namespace kube-system
   - Почему подозрительно: Сервисный аккаунт monitoring пытается получить доступ к секретам в системном namespace, что является попыткой эскалации привилегий.

2. Привилегированные поды:
   - Кто: Пользователь, выполняющий скрипт (скорее всего, admin)
   - Комментарий: Создание привилегированного пода позволяет контейнеру получить доступ к хостовой системе, что может привести к компрометации всего кластера.

3. Использование kubectl exec в чужом поде:
   - Кто: Пользователь, выполняющий скрипт
   - Что делал: Выполнял команду cat /etc/resolv.conf в поде CoreDNS без необходимости, что может быть признаком разведки.

4. Создание RoleBinding с правами cluster-admin:
   - Кто: Пользователь, выполняющий скрипт
   - К чему привело: Сервисный аккаунт monitoring получил права cluster-admin, что является полной компрометацией RBAC.

5. Удаление audit-policy.yaml:
   - Кто: Пользователь под именем admin
   - Возможные последствия: Отключение аудита позволяет злоумышленнику скрыть дальнейшие вредоносные действия в кластере.

## Вывод

Обнаружены множественные попытки компрометации кластера Kubernetes:
1. Несанкционированный доступ к секретам
2. Создание привилегированных контейнеров
3. Исполнение команд в чужих подах
4. Эскалация привилегий через RoleBinding
5. Попытка отключения системы аудита

Рекомендации:
1. Ужесточить политики RBAC
2. Запретить создание привилегированных подов
3. Регулярно мониторить audit-логи
4. Ограничить использование exec в production-средах
5. Внедрить принцип наименьших привилегий для сервисных аккаунтов
